# Agent 工具调用容错设计

> 来源：小林 coding《面试官：Agent 调工具时遇到格式非法、参数错误或者接口超时，你会怎么处理？》学习笔记，结合 VitaFlow 工具链现状逐条对照。
>
> 核心主线一句话：**容错方案取决于故障发生在哪一层、这次失败有没有产生外部副作用。**

---

## 〇、总框架

把一次工具调用拆成「决策 → 校验 → 执行 → 确认 → 恢复」五个阶段，每个阶段用不同的处理方式：

```
模型决策 → 结构校验 → 业务校验 → 权限校验 → 执行（重试/熔断）→ 确认（幂等/查状态）→ 恢复（Checkpoint/转人工）
```

反面教材（面试里最容易被追问打穿的回答）：

> 「统一重试三次，失败再返回错误。」

追问链条：参数错误重试三次有什么用？下游过载时大家一起重试会不会压得更死？超时发生在发邮件之后、响应返回之前呢——重试就发两封。模型修好的参数就一定有权限执行吗？幂等键需要服务端配合，Prompt 代替不了服务端鉴权。

---

## 一、错误先分类再处理

失败提示一样，根因完全不同，处理策略必须分开：

| 故障类别 | 常见例子 | 推荐动作 |
|---|---|---|
| 模型决策/格式错误 | 工具名不存在、JSON 非法、缺字段 | 返回结构化校验反馈，让模型有界重生成 |
| 参数/业务校验失败 | 日期范围错误、订单不存在、余额不足 | 修正可确定的格式；缺信息问用户；业务失败重新规划 |
| 鉴权与权限失败 | 凭证失效、用户无权执行 | 刷新可刷新的凭证；越权直接拒绝并审计 |
| 瞬时基础设施故障 | 连接失败、429、部分 5xx | 安全重放 + 预算允许时有界重试 |
| 明确执行失败 | 下游确认事务已回滚 | 按业务规则降级、换工具或结束任务 |
| 副作用结果未知 | 写请求超时、响应前断连 | 幂等键查状态或对账，**不能盲目重试** |

要点：

- HTTP 状态码只是线索，重试决策还要结合**工具语义和执行阶段**。连接建立前失败 → 服务端大概率没收到；读响应时超时 → 服务端可能已经执行完了。
- 同一个「失败」发生在哪一层，决定它属于哪一类。

## 二、调用前三道门

在真正执行**之前**依次拦截：

1. **结构校验**：工具名存在、JSON 合法、必填字段齐、类型/枚举/取值范围对。能用模型原生结构化输出或受约束解码时先约束，宿主程序仍要按 JSON Schema 复查。系统只做无歧义的规范化（如去首尾空格），不能靠正则猜出收件人、金额、文件路径。
2. **业务校验**：`amount` 是数字只说明格式对，不说明金额可退；需要查当前业务状态——资源是否存在、版本是否冲突、前置条件是否满足。
3. **权限与风险校验**：服务端按已认证的用户身份计算权限，最小权限控制；删除数据、付款、群发等高风险动作进入审批。**Prompt 里写「你只能操作自己的数据」不算权限控制——提示词不是安全边界。**

**VitaFlow 对照**：TypeBox Schema（ai-service）→ 数值反幻觉/字段白名单/id 有界合并（backend `validate_*`）→ `require_ai_service_token` + `get_resume(user_id, resume_id)` 归属校验，三道门齐全。

## 三、统一错误信封

工具失败返回**固定格式**，而不是甩堆栈或一句「调用失败」：

```yaml
ok: false
call_id: tc_8f21
tool: send_email
error:
  category: rate_limit      # 哪一类故障（对应第一节的分类）
  retryable: true           # 重试有没有意义
  outcome: not_started      # 副作用状态：not_started / failed / succeeded / unknown
  retry_after_ms: 1200      # 服务端建议的等待时间
  safe_message: 服务暂时限流  # 给模型/用户看的脱敏信息
```

为什么必须统一：

- 原始堆栈塞回模型 → 可能泄露内部路径和密钥，模型也读不懂；
- 一句「调用失败」塞回模型 → 模型不知道该重试、改参数还是问用户；
- `category` 供策略引擎/监控按类别统计失败率、配告警；`outcome` 告诉重试器能不能安全重试。

注意：`retryable: true` 只是必要条件，不是充分条件——工具无法安全重放、任务总时限耗尽、用户已取消时都不应再重试。

**VitaFlow 现状**：工具端点失败只返回裸 `{"ok": false, "reason": "..."}`，无类别。改进方向：加 `category`（validation 参数错可修 / business 业务失败需重规划 / infra 服务暂不可用），模型和监控都能按类别决策。

## 四、有界重试 + 退避抖动

只对瞬时故障（连接失败、429、503）重试，同时看**错误类型、调用语义、尝试次数、剩余时间**四项：

- **单次超时 + 总 Deadline**：每次重试前确认「退避等待 + 下一次调用」不会超过剩余预算；
- **指数退避 + 随机抖动（jitter）**：1s → 2s → 4s…再加随机量。不加抖动，N 个实例同时失败又同时重试，形成「重试风暴」再次打垮下游；
- **尊重 Retry-After**：下游明确给建议时优先遵守；
- **重试只放一层（重试的层级归属）**：SDK、工具适配层、Agent 调度层如果各重试 3 次，请求次数会相乘放大。让最了解幂等性的那一层负责，其他层关掉自动重试。详见下文。
- **取消要向下传播**：用户停止或 Deadline 到期后，取消未开始的调用、通知执行中的工具停止（客户端结束等待 ≠ 服务端代码自动停止）。

### 补充：「让最了解幂等性的那一层负责」是什么意思

**问题：一条调用链上有很多层，每层都可能自带默认重试。**

一次 AI 请求的调用链（VitaFlow 实例）：

```
前端 → FastAPI（backend）→ ai-service（Node）→ 模型厂商 API
                                    └→ 工具回调 → FastAPI
```

每一层都可能遇到网络抖动。如果每层都重试 3 次（1 次原始 + 2 次重试）：

- ai-service 对模型 API：失败后自己重试，最多发 3 个请求；
- FastAPI 对 ai-service：不知道刚才那 3 个请求的事，它只看到最终失败，于是自己也重试 3 轮——而每轮里面 ai-service 又重试 3 次。

数学上 `3 × 3 = 9`，三层就是 `27`。**一次瞬时抖动被放大成 27 倍流量**——如果下游刚好是因过载才失败的，这些重试会让它彻底雪崩（重试风暴的典型成因）。

**为什么归给「最了解幂等性的那一层」：重试的前提是安全（不会造成重复副作用），而"安不安全"只有特定位置知道。** 工具适配层最清楚这个工具是只读还是写操作、有没有幂等键；任务调度层最清楚总时间预算还剩多少、用户是否已取消。重试决策应放在拥有最多上下文的那一层。

**「其他层关掉」怎么落地**：显式关掉 HTTP 库的自动重试，失败原样上抛：

```python
# FastAPI 调 ai-service：不做自动重试，把失败抛给上层决策
client = httpx.AsyncClient(timeout=..., retries=0)
```

整条链只有一处做有界重试，其余层只管把错误向上传。

**VitaFlow 现状**：已接近这个理想态——backend → ai-service 的 httpx 没配自动重试，ai-service → FastAPI 工具回调的 fetch 也没有重试，失败直接把错误文本回给模型。因此「给计费回调加重试」的正确做法是**只在这一处加**（3 次有界重试），整条链依然只有一个重试点，不会放大。

## 五、熔断、降级、故障转移

重试解决「短暂抖动」，这三个解决「持续故障」：

- **熔断**：连续失败/错误率达标后进入 Open（快速失败，不打下游），冷却后放少量探测请求（Half-Open），成功则回 Closed。类比空气开关。
- **降级**：熔断后换弱路径——返回缓存旧数据、只读模式、语义等价的备用服务。必须**明确告知模型数据陈旧/缺哪些字段**，防止模型把残缺结果包装成完整答案。
- **故障转移的边界**：两个搜索服务可互换；两个支付渠道不共享交易状态和幂等范围时，切换可能两笔扣款。备用工具必须满足相同的权限、一致性、副作用约束。

**VitaFlow 判断**：单机 loopback、单一下游，做了是过度设计——这也正是面试考点：方案要匹配部署形态。

## 六、幂等键 + Checkpoint 处理「结果未知」

全文最难点。场景：调用「发邮件」超时，邮件**可能已经发出**——重试可能发两封，不重试可能一封没发。断连意味着调用方**永远无法确定**第一次的结果。

- **幂等键**：首次调用前生成稳定唯一键（如 `run_id + step_id`），重试/重启/人工恢复都复用它；服务端持久化「键 → 参数摘要 → 状态 → 结果」，同键同参返回已有结果，同键异参拒绝。业务写入与幂等记录同一事务边界，或用 Outbox + 对账补偿收敛。
  - 边界：下游不支持去重、记录过期、一次调用跨多个系统，都可能部分成功。更准确的目标是 **at-least-once 投递 + 幂等去重 = 业务效果恰好一次**，而不是无条件的 exactly-once。
- **Checkpoint**：副作用调用前持久化「当前步骤、工具名、参数摘要、幂等键、status=pending」，拿到确定结果后更新为 succeeded/failed。重启后恢复器：已成功跳过、明确失败可重规划、pending/unknown 先按键查下游状态——**绝不重跑整个计划**。
- **转人工**：状态查询仍无法确认时暂停、保存现场、交人工（批准重试/改参数/执行补偿/终止）。高风险操作也可在首次执行前主动暂停让用户确认。

面试标准闭环：**校验 → 写 Checkpoint → 带幂等键执行 → 超时按键查状态 → 确认没执行才重试 → 查不清转人工**。

**VitaFlow 判断**：架构性绕开了这个问题——工具本身只做校验（无副作用），真正写库要等用户点确认（Pending/Apply/Reject 状态机）。副作用被人审这道闸挡住，不需要幂等键。这一点本身就是好的面试素材：**用架构消灭一类问题，比用代码解决它更优**。

## 七、完整 Trace 审计

线上告警只有「工具失败」没有排查价值。一次 Trace 至少串起 `run_id → step_id → tool_call_id`，并记录：

- 工具及 Schema 版本、模型与 Prompt 版本；
- 参数脱敏摘要、调用方身份、起止时间；
- 每次尝试、错误类别、重试/降级决策、Checkpoint 状态、最终结果；
- 审计额外记录：谁批准了高风险动作、批准时的参数、系统实际执行了什么；
- 指标关注：各工具成功率、延迟分位数、重试率、熔断状态、unknown 结果数、幂等去重次数、人工接管量。

有了它才能回答三个生产问题：**失败发生在哪一层？系统为什么选择重试或停止？这次副作用最终有没有发生？**

**VitaFlow 现状**：`tool_trace` 逐条落库 + `ai_tasks` 记 token/模型/状态 + 管理看板，是最简版；缺单次调用耗时、错误类别、失败原因聚合。

## 八、对照总结与改进清单

| 文章概念 | VitaFlow 现状 | 结论 |
|---|---|---|
| 错误分类 | 校验失败回传模型重试，但无类别 | 改进（错误信封的 category） |
| 三道门 | Schema / 业务校验 / 归属校验齐全 | 已达标 |
| 错误信封 | 裸 `ok+reason` 字符串 | **改进优先级 1** |
| 有界重试 | 计费回调 `/service/usage` 失败即丢 | **改进优先级 3**：3 次退避重试 + 对账日志 |
| 熔断/降级/转移 | 无 | 不做（单机单下游，过度设计） |
| 幂等键/Checkpoint | 无副作用设计 + 用户确认，天然规避 | 已达标（架构层面） |
| Trace 审计 | tool_trace + ai_tasks + 看板 | 已达标（可加耗时/类别） |

按性价比排序的落地项：

1. **统一错误信封**：backend 工具端点返回 `{ok, category, retryable, reason}`，工具层映射为模型可读文案，trace 记 category。
2. **runTask JSON 修复重生成**：一次性任务解析失败时，把 parse 错误喂回模型做一次有界重生成（现直接报错让用户重试整个任务）。
3. **计费回调重试/对账**：ai-service → FastAPI `/service/usage` 加有界重试，失败落日志供对账（系统里唯一真正的「结果未知」场景）。
4. **工具回源 fetch 超时**：`postSectionUpdate` 等未设 timeout，后端卡住会挂到 turn 超时，补短超时 + 明确报错。

明确不做：熔断/降级/故障转移、幂等键/Checkpoint——工具无副作用 + 人审确认流程已规避该类问题，引入即过度设计。
