## 1. 项目总览

**VitaFlow（简历流）** 是一个智能简历生成与优化平台，核心卖点是 AI 驱动的简历编辑、诊断和 JD 匹配优化。

### 技术栈

| 层 | 技术 | 为什么选它 |
|---|------|-----------|
| 后端 | FastAPI + SQLAlchemy 2.0 + Alembic | 异步友好、类型安全、自动生成 OpenAPI 文档 |
| AI | LangChain + LangGraph + ChatOpenAI | 标准化的 LLM 调用/流式/多步编排 |
| 前端 | Vue 3 + TypeScript + Pinia | 响应式状态管理，组合式 API 适合复杂编辑器 |
| UI | shadcn-vue + Tailwind v4 + Lucide | 无样式锁定、高度可定制 |
| 导出 | Playwright + WeasyPrint + python-docx | 双渲染器兜底，Chromium 主 + WeasyPrint 备 |
| 存储 | MinIO / 阿里云 OSS | 开发自测用 MinIO，生产用 OSS，统一抽象 |

### 核心功能模块

```
用户注册/登录（邮箱验证 + JWT）
  → 简历编辑（模块化表单 + 实时预览）
    → AI 功能（生成/评分/优化/JD 匹配/对话）
      → 导出（PDF / Word）
```

## 2. 后端分层架构

```
backend/app/
├── api/          ← 路由层：HTTP 边界，请求解析 + 响应包装
├── schemas/      ← Pydantic 模型：入参校验 + 出参序列化
├── services/     ← 业务逻辑：唯一放 domain rules 的地方
├── models/       ← ORM 模型：纯表定义，无业务逻辑
├── core/         ← 基础设施：配置/数据库/安全/异常/响应
└── static/ & templates/  ← 简历渲染资源
```

### 为什么这么分层？

**面试回答要点：**

1. **API 层零业务逻辑**：路由函数只做三件事 —— 拿依赖（`Depends(get_db)`, `Depends(get_current_user)`）、调 service、包 `success()` 响应。这样路由函数可以纯 mock 测试。

2. **Schema 隔离 ORM**：Pydantic schema 用 `model_config = {"from_attributes": True}`，可以直接从 SQLAlchemy 对象序列化，但**永远不会把 ORM 对象直接返回给前端**。这防止了：
   - 敏感字段泄漏（如 `password_hash`）
   - 数据库结构变更影响 API 契约
   - 循环引用导致的序列化崩溃

3. **Service 框架无关**：service 函数接收 `Session` + 纯参数，不依赖 FastAPI 的 `Request`/`Response`。这意味着可以用纯 pytest + 内存 SQLite 测试业务逻辑，不需要启动 HTTP 服务器。

4. **统一响应信封**：所有接口返回 `{"code": 200, "message": "success", "data": ...}`，即使是校验错误也变成 `{"code": 422, "message": "请填写密码"}`。这是国内常见的"业务信封"模式，前端只需要判断 `code` 就能统一处理错误。

### 关键设计模式

| 模式 | 实现 | 解决什么问题 |
|------|------|-------------|
| 依赖注入 | `Depends(get_db)`, `Depends(get_current_user)` | 会话自动关闭、认证透明 |
| 业务信封 | `success(data)` / `error_response()` | 前端统一错误处理 |
| 友好校验 | `friendly_validation_message()` | Pydantic 英文错误转中文 |
| JSON 文档模型 | `resume_data` 单列 JSON | 简历的 schema 灵活可变，不用改表 |

## 3. 简历数据模型：为什么用 JSON 列而不是关系表？

这是面试高频问题。

### resume_data 的结构

```json
{
  "basics": { "name": "张三", "phone": "...", "field_config": {...} },
  "summary": { "content": "Markdown 文本" },
  "education": [{ "id": "edu_1", "school": "...", ... }],
  "skills": [{ "id": "skill_1", "name": "...", "keywords": [...] }],
  "work": [{ "id": "...", "company": "...", ... }],
  "projects": [{ "id": "...", "name": "...", "highlights": [...] }],
  "awards": [{ "id": "...", ... }],
  "custom_sections": [{ "id": "custom_1234", "title": "自定义模块", "items": [...] }],
  "layout": {
    "section_order": ["basics", "summary", "education", ...],
    "hidden_sections": [],
    "section_titles": { "work": "工作经历", ... }
  }
}
```

### 为什么不用关系表？

| 方案 | 优势 | 劣势 |
|------|------|------|
| **关系表** | 数据完整性强、可跨简历查询 | section 可动态增删/重命名/重排序，需要大量多对多表；改 schema 要 migration |
| **JSON 列**（选用） | schema 灵活、前后端同构、改结构零 migration | 无法跨简历 SQL 查询；JSON 可能损坏 |

**核心论点**：简历是**文档型数据**，不是关系型数据。用户需要：
- 自由拖拽排序 section（`section_order`）
- 随意隐藏/重命名 section（`hidden_sections`, `section_titles`）
- 添加自定义 section（`custom_sections`）
- 每个联系字段的显示配置独立控制（`field_config`）

如果用关系表，这些需求需要 `section_order` 表、`section_config` 表、`field_config` 表……每加一个灵活性需求就多一张表。JSON 列一步到位。

### 双侧归一化（Defense-in-Depth）

前端 `normalizeResumeData()` 和后端 `_prepare_resume_data()` **都**会确保：
- 所有内置 section 存在（缺失则补默认值）
- `section_order` 包含所有 section，`basics` 永远排第一
- `hidden_sections` 不含 `basics`
- `field_config` 包含所有 8 个必需字段

为什么两边都做？因为前端可能发送部分数据（网络中断、旧版缓存），后端也可能读到历史脏数据。双重保障确保渲染永远不会因缺失字段而崩溃。

## 4. 认证流程

```
注册：发送验证码 → 验证邮箱 → 注册
登录：email + password → JWT（HS256, 24h 过期）
鉴权：每个请求 Authorization: Bearer <token> → get_current_user 依赖
```

### 安全要点

1. **验证码不存明文**：存储 `sha256(code)`，校验用 `hmac.compare_digest()`（常量时间比较，防时序攻击）
2. **验证码一次性**：使用后标记 `used=True`，不可重放
3. **密码 bcrypt**：passlib 的 `CryptContext(schemes=["bcrypt"])`，自动加盐
4. **JWT subject 是 user_id**：不存 email/username 等可变信息，避免 token 中信息过期
5. **前端 401 自动清理**：axios 响应拦截器检测到 401 → 删除 token → 跳转登录页

## 5. 简历渲染管线

这是从数据到可视化的完整链路：

```
resume_data + template_id + template_config
    ↓
_prepare_resume_data()         ← 后端归一化 + avatar URL 重写 + 构建 _sections 列表
    ↓
Jinja2 模板渲染                ← 4 套模板：classic/tech/modern/blue_timeline
    ↓                          ← 自定义过滤器：markdown / css_font_family / font_face_css / split_tags
    ↓
HTML 字符串                    ← 完整文档，内嵌 CSS + @font-face + SVG 图标
    ↓
前端 PreviewFrame.vue          ← iframe 分页预览（见第 6 节）
  或
后端 PDF 导出                   ← Chromium/WeasyPrint 渲染（见第 7 节）
```

### Jinja2 自定义过滤器

| 过滤器 | 作用 |
|--------|------|
| `\| markdown` | Markdown → 安全 HTML（bleach 白名单消毒） |
| `\| css_font_family` | 字体预设名 → CSS font-family 栈（含中文回退链） |
| `\| font_face_css` | 生成 @font-face 声明（指向 woff2 文件） |
| `\| split_tags` | 逗号/分号分隔 → 标签数组（去重） |

### 字体预设系统

| 预设 | 字体 | 场景 |
|------|------|------|
| `vf-sans` | Noto Sans SC | 通用现代 |
| `vf-serif` | Noto Serif SC | 正式传统 |
| `vf-rounded` | HarmonyOS Sans SC | 创意亲和 |
| `vf-kai` | LXGW WenKai | 文化气质 |

每个预设都有完整的 CSS 回退链（macOS/Windows/Linux 中文字体），确保任何平台都能正确显示。

## 6. 前端 iframe 分页预览机制

这是前端最复杂的部分。核心挑战：**在浏览器中精确模拟 A4 分页**。

### 架构

```
服务端渲染的 HTML
    ↓
[隐藏的测量 iframe]              ← 全尺寸，opacity: 0
  - 加载完整 HTML（不裁剪）
  - 测量 A4 像素高度（创建 297mm 高 div → getBoundingClientRect）
  - 测量内容实际高度（扫描所有叶子节点的 rect.bottom）
  - 计算 pageSlices[]（每页的偏移量 + 可视区域）
    ↓
[可见的页面 iframe] × N          ← 每页一个 iframe
  - 210mm × 297mm，overflow: hidden
  - 加载同一份 HTML，但注入不同 CSS：
    .resume-page { transform: translateY(-sourceTopMm mm); }
  - 用 transform 平移 + overflow 裁剪，形成"视窗"效果
  - 外层 scale 缩放控制预览大小
```

### 为什么用 iframe 而不是 div？

1. **CSS 隔离**：简历模板有自己的全局样式，如果直接渲染在主文档中会污染编辑器 UI
2. **精确尺寸**：iframe 可以设置 `width: 210mm; height: 297mm`，浏览器精确计算 mm → px
3. **独立字体加载**：iframe 有自己的 `document.fonts`，不与主文档共享

### 分页计算的关键细节

- **首页和后续页可以有不同的边距**：通过 CSS 自定义属性 `--page-margin-top` / `--page-margin-next-top` 控制
- **用叶子节点测量高度**：避免容器 padding 导致的双重计算
- **重测量策略**：ResizeObserver + MutationObserver + 图片 onload + 多次 setTimeout（0/80/180/420/900ms）捕捉字体加载和图片尺寸导致的布局偏移
- **防无限循环**：最多 80 页

## 7. PDF 导出：双渲染器 + SHA-256 缓存

### 整体流程

```
get_pdf_path(resume)
    ↓
计算指纹 → 查缓存 → 命中则直接返回
    ↓（未命中）
获取 per-resume 锁（防并发重复渲染）
    ↓
render_resume_html() → HTML
    ↓
尝试 Chromium 渲染 → 成功则写入缓存
    ↓（失败）
尝试 WeasyPrint 渲染 → 成功则写入缓存
    ↓（都失败）
HTTPException 500
```

### SHA-256 缓存指纹

```python
fingerprint = sha256({
    "cache_version": "2026-06-18-2",       # 手动 bust 字符串
    "renderer": "chromium" | "weasyprint",
    "renderer_signature": sha256(模板HTML+CSS+静态文件),  # 模板变更也 bust
    "resume_data": ...,
    "template_config": ...,
    "pdf_base_url": ...,
})
```

任何输入变化 → 指纹变化 → 缓存失效。`renderer_signature` 哈希了整个模板目录，所以**部署新模板也会自动 bust 缓存**。

### Chromium 渲染步骤

1. Playwright 启动无头 Chromium（`--no-sandbox --disable-gpu`）
2. `page.route()` 拦截所有网络请求 → 上传文件直接从对象存储读取，不走 HTTP
3. `page.set_content(html)` 加载 HTML
4. 等待 `document.fonts.ready`（确保自定义字体加载完）
5. `page.evaluate(PAGINATION_SCRIPT)` — 页内防孤行调整
6. `page.evaluate(PAGED_EXPORT_SCRIPT)` — 将文档切成 A4 页
7. `page.pdf(format="A4", margin=0)`

### WeasyPrint 渲染

- 自定义 `url_fetcher`：当 WeasyPrint 请求资源时，匹配到上传文件/字体 → 直接从存储读取，不走 HTTP
- 这是**降级方案**：Chromium 不装时自动走 WeasyPrint

### 并发控制

- `threading.Lock` 按 resume ID 分配，同一简历不会并发渲染两次
- 双检锁：锁外查缓存（快速路径），锁内再查一次（等锁期间其他线程可能已渲染完）

## 8. 存储抽象：MinIO / 阿里云 OSS

### 策略模式

```python
def _provider():
    if settings.storage_provider == "minio": return _minio_client()
    elif settings.storage_provider == "aliyun_oss": return _oss_bucket()
```

所有操作（上传/读取/流式）都通过统一函数，内部按 provider 分发。

### 两种 URL 模式

| 模式 | file_url 指向 | 优缺点 |
|------|---------------|--------|
| `proxy` | `后端/api/files/{object_name}` | 存储可内网部署、无 CORS 问题；但后端承压带宽 |
| `public` | 存储直接公开 URL | 后端零带宽、可 CDN 加速；但存储必须公开、需配 CORS |

## 9. 前端状态管理与编辑器交互

### Pinia Store 分工

| Store | 职责 |
|-------|------|
| `useUserStore` | token 存取、用户信息 |
| `useResumeStore` | 简历 CRUD、归一化、预览刷新 |
| `useEditorStore` | UI 状态：当前 section、保存状态、缩放 |

### 编辑器自动保存机制

```
用户修改表单 → 修改 resumeStore.resumeData（本地）
  → markChanged() → editor.saved = false
  → debouncedSave()（1.5s 防抖）
    → performSave()
      → PUT /api/resumes/{id}
      → refreshPreviewHtml()（更新预览）
```

**关键设计**：
- **Promise 链序列化**：`saveChain = saveChain.then(() => performSave())`，防止保存请求重叠
- **预览请求序列号**：`previewRequestSeq` 递增，响应回来时检查是否已过期，丢弃旧响应
- **编辑模式 vs AI 模式**：两个模式共享同一个 store 数据，但 UI 完全不同（表单 vs 聊天），通过 `mainMode` 切换

## 10. 关键架构决策总结

| 决策 | 选择 | 理由 |
|------|------|------|
| 简历存储 | JSON 列而非关系表 | 文档型数据，schema 需灵活可变 |
| 前后端归一化 | 双重 normalize | 防御性编程，任一侧数据不全都能兜底 |
| 分页预览 | iframe + transform | CSS 隔离 + 精确 mm 尺寸 + 独立字体加载 |
| PDF 渲染 | 双渲染器 | Chromium 主力 + WeasyPrint 兜底，部署灵活 |
| PDF 缓存 | SHA-256 全输入指纹 | 任何变化自动 bust，包括模板部署 |
| AI 输出 | JSON 严格校验 + 三层修复 | LLM 输出不可信，必须防御性解析 |
| AI 变更 | Pending/Apply/Reject | 用户必须显式确认，AI 不能直接改简历 |
| AI 幻觉 | 数字声明验证 | 阻止 AI 编造不存在的量化结果 |
| 存储抽象 | 策略模式 | 开发 MinIO / 生产 OSS 零代码改动 |
| 响应信封 | `{code, message, data}` | 前端统一错误处理，HTTP 状态码仅表传输层 |
