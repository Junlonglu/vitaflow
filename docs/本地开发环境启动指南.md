# VitaFlow 本地开发环境启动指南

> 本文档记录本机（Windows）的完整启动流程。基础设施全部由 Docker 管理，前后端在本机运行。

## 架构总览

| 服务 | 运行方式 | 地址 | 说明 |
|------|---------|------|------|
| MySQL 8.0 | Docker `vitaflow-mysql` | 127.0.0.1:3306 | root/123456，库 `vitaflow` |
| Redis 7 | Docker `vitaflow-redis` | 127.0.0.1:6379 | 无密码 |
| MinIO | Docker `vitaflow-minio` | API :9000 / 控制台 :9001 | minioadmin/minioadmin |
| 后端 FastAPI | 本机 uvicorn | http://127.0.0.1:8000 | 接口文档 `/docs` |
| 前端 Vue 3 + Vite | 本机 npm | http://localhost:5173 | |
| AI 服务 | 本机 tsx | http://127.0.0.1:8300 | 可选，pi-agent 旁路，见 `ai-service/` |

所有容器配置见项目根目录 `docker-compose.yml`，数据持久化在 named volume 中（`mysql-data`、`redis-data`、`minio-data`）。

## 日常启动流程

```bash
# 1. 启动 Docker Desktop（手动打开），等待其就绪

# 2. 启动全部基础设施
docker compose up -d

# 3. 数据库迁移（有新迁移时才需要）
cd backend
./.venv/Scripts/alembic.exe upgrade head

# 4. 启动后端（端口 8000）
cd backend
./.venv/Scripts/uvicorn.exe app.main:app --reload --host 0.0.0.0 --port 8000

# 5. 启动前端（端口 5173）
cd frontend
npm run dev

# 6. 启动 AI 服务（可选，pi-agent 骨架；需先 cd ai-service 且 npm install）
cd ../ai-service
cp .env.example .env            # 设置 AI_SERVICE_TOKEN，与 backend/.env 的 AI_SERVICE_TOKEN 一致
npm run dev
```

> 开启 AI 服务代理：在 `backend/.env` 置 `AI_SERVICE_ENABLED=true`、`AI_SERVICE_TOKEN=<与 ai-service 相同>`，并保持 `AI_SERVICE_URL=http://127.0.0.1:8300`。上下文注入的历史条数由 `AI_SERVICE_CONTEXT_MESSAGES` 控制（默认 12，范围 1-40）。关闭时走原 LangChain 链路。
>
> 简历修改工具链（`update_basics_field` 字段级 + `update_section`/`propose_change` 模块级）：Agent 调用工具后，回调 `backend` 的 `/api/ai/service/tool/*` 端点做数值防幻觉校验并返回待确认修改载荷（不落库），`stream_ai_service_chat` 收到 `result` 事件里的 `pending_change` 后落库为待确认消息，前端点击「应用/拒绝」走现有 `/decision` 接口。`get_resume_context` 按需读取模块。`ai-service/.env` 的 `PI_FASTAPI_BASE_URL` 指向 backend 基址（默认 `http://127.0.0.1:8000`）。

### 对话内快捷指令（/润色 · /翻译 · /优化 · /生成）

四个高频操作做成了对话内快捷指令，直接输入到 AI 聊天框即可触发。它们不是独立管线：指令会被展开为一条指令性提示词（pi-agent PromptTemplate，`$@` 代入用户参数），模型随后走**与自然语言完全相同的工具/校验链路**（`get_resume_context` → `update_section`/`propose_change` → 后端数值校验 → 待确认 → 用户应用/拒绝）。未设指令的能力仍可用自然语言触发。

| 指令 | 用途 | 参数 |
|------|------|------|
| `/润色 <模块>` | 润色指定模块的表达（只改措辞，不改事实） | 模块名，如 工作经历 / 项目经历 / 教育经历 / 个人简介 / 专业技能 / 荣誉奖项 / 自定义模块 |
| `/翻译` | 整份简历中英互译（保结构、事实与顺序） | 无 |
| `/优化 <JD>` | 基于粘贴的岗位描述定向优化简历匹配度；先 `get_resume_context` 读模块，再 `propose_change` 生成待确认方案（多步工具调用） | 粘贴的岗位描述 JSON/文本 |
| `/生成` | 根据目标岗位生成简历（缺关键信息时先一句追问，再生成待确认方案） | 目标岗位 |

> 约束与工具链一致：只在「已有证据」边界内优化，不把 JD 要求写成已掌握能力、不新增事实、不编造量化结果；结果始终是待确认修改，需用户确认后写入。真实模型识别/调用这些指令需 Docker MySQL + API Key 联调，Faux 演示中 `/润色` 走 `update_section`、`/优化` 走「读模块 → propose_change」的同一代码路径。

### 多模态图片输入（上传图片）

求职者上传简历图片/截图后，图片驱动简历修改走**同一条** section 工具 + 待确认变更链路，不另建管线：

```
前端上传图片 → FastAPI 落库用户消息 → 代理把 MinIO/OSS 对象解析为 base64 ImageContent[]
  → 传给 AI 服务 images 字段 → session.prompt(text, { images }) 原生附加给模型
  → 模型结合图片调用 get_resume_context / update_section / propose_change → FastAPI 数值校验 → 待确认 → /decision
```

| 环节 | 要点 |
|------|------|
| 图片格式 | 仅 jpg/png/webp，≤5MB；上传即返回 url + object_name |
| 代理转换 | FastAPI 侧用 `read_uploaded_file(object_name)` 读字节→base64；无 object_name/非图片/读取失败则跳过（不破坏纯文本轮次） |
| 本服务接收 | `server.ts` 解析 `images: [{data, mimeType}]`，express JSON 上限已提到 20mb |
| 模型需声明 | **vision 模型的 `models.json` 必须写 `"input": ["text","image"]`**，否则 provider 静默丢弃图片块（pi 只对声明 image 输入的模型转发） |
| 多模态开关 | 后端 `supports_multimodal=false` 时直接报错「当前模型未开启多模态能力」，而非静默丢弃（与旧 LangChain 链路一致） |

> **vision 兼容性实测结论**：pi-agent 图片输入用 base64 data-URL（provider 自拼 `data:<mime>;base64,<data>`，`ImageContent.data` 是裸 base64）。本服务与代理已按此约定实现，Faux 演示中图片走「读模块 → propose_change」确定性序列验证同一代码路径。**目标模型 deepseek-v4-flash-vision-exp 对图片的实际识别与多步调用需 Docker MySQL + API Key 联调（环境阻断，成功/受限待实测）**；理论兼容，受「image 输入声明 + base64 data-URL」两项约束。

### 真实模型接入（PI_PROVIDER=real）与按模型计费

AI 服务默认 `PI_PROVIDER=faux`（本地确定性、无网络）。要接真实模型：

```bash
cd ai-service
mkdir -p .pi-agent && cp models.json.example .pi-agent/models.json   # 按需改模型列表
# .env：PI_PROVIDER=real，并设置 DEEPSEEK_API_KEY（models.json 以 $DEEPSEEK_API_KEY 引用，密钥不落盘）
npm run dev
```

| 项 | 说明 |
|----|------|
| models.json | 顶层 `{"providers": {"<provider-id>": {...}}}`；DeepSeek 走 `openai-completions` API，compat 覆盖项见 `models.json.example`（`supportsDeveloperRole: false` 等） |
| 模型选择 | 请求 `model` 字段 = `AiModelConfig.pi_model_ref`（`provider/model`），管理后台可配；未带时取 models.json 第一个已认证模型 |
| 计费 | 成功轮次结束后，AI 服务按 `provider/model` 归集 token 用量（pi `message_end` 的 usage，工具循环逐次求和）POST 回 `/api/ai/service/usage`；FastAPI 按 `pi_model_ref` 反查模型计费率，走与旧链路相同的 task + `settle_task_flow_points` 账本入账（对账一致），未映射 ref 按默认 ai_chat 规则兜底 |

> 数据库侧：`ai_model_configs` 新增 `pi_model_ref` 列（迁移 `0028_pi_model_ref`），管理后台「AI 配置」表单可填。真实模型对话/工具调用/token 用量的端到端实测需 API Key 联调（环境阻断，待实测）。

## 注意事项

### 本机 MySQL 已停用

本机原来装有 MySQL 8.0（Windows 服务名 `MySQL`），为避免与 Docker 抢占 3306 端口，已**停止并改为手动启动**（`DEMAND_START`）。因此重启电脑后它不会自动运行，Docker MySQL 可正常接管 3306。

如需临时使用本机 MySQL：

```powershell
# 管理员权限执行；先 docker stop vitaflow-mysql 释放端口
net start MySQL
net stop MySQL
```

### 端口占用排查

服务起不来时先查端口占用：

```bash
netstat -ano | findstr "LISTENING" | findstr ":3306 :6379 :9000"
```

### 首次启动

首次 `docker compose up -d` 会拉取 mysql:8.0 镜像（约 170MB），耐心等待即可。MySQL 容器自带 healthcheck，可用以下命令确认就绪：

```bash
docker inspect vitaflow-mysql --format "{{.State.Health.Status}}"   # 期望 healthy
```

## 依赖与镜像版本策略

### Docker 镜像

| 镜像 | 标签策略 | 说明 |
|------|---------|------|
| mysql | `8.0`（锁定大版本） | 小版本更新安全，风险低 |
| redis | `7-alpine`（锁定大版本） | 同上 |
| minio | 锁定到具体版本 `RELEASE.2025-09-07T16-13-09Z` | MinIO 曾有破坏性变更，不用 `latest` |

升级 MinIO 时手动改标签并验证：先 `docker compose pull minio`，再 `up -d`，出问题可回退旧版本号。

### 前端依赖

上游项目的 `package.json` 大量使用 `"latest"` 作为版本号，导致：

1. 不同时间执行 `npm install` 会得到不同版本，lockfile 频繁漂移；
2. 与上游同步时 `package-lock.json` 几乎必然冲突。

应对方式：**保持与上游一致，不主动改 package.json**；lockfile 提交在仓库里保证日常安装可复现。遇到冲突时的快速解决法：

```bash
git checkout --theirs frontend/package-lock.json   # 或 --ours 取自己这边
cd frontend && npm install                         # 重新生成一致的 lockfile
```

若某次重新安装后构建报错（如依赖发大版本），可在 lockfile 中查到之前可用的精确版本，临时把 package.json 对应项固定到该大版本内。

## 数据备份与恢复

### 导出（从 Docker MySQL 备份）

```bash
docker exec vitaflow-mysql mysqldump -uroot -p123456 \
  --single-transaction --routines --triggers vitaflow > backup.sql
```

> 注意：输出重定向时不要写 `2>&1`，否则密码警告文本会混入 SQL 文件导致导入失败。

### 恢复（导入到 Docker MySQL）

```bash
docker exec -i vitaflow-mysql mysql -uroot -p123456 vitaflow < backup.sql
```
