# AI 功能链路分析与耗时排查

> 以「AI 助手把简历地点从广州改成深圳」为案例，分析对话改简历的完整调用链、各环节实测耗时、一致性保障机制，以及 LangChain / LangGraph 在其中的具体角色。

---

## 1. AI 助手对话改简历的工作流程

```
浏览器（AiChat 组件）
  → POST /api/ai/resume-chat/{id}/messages[/stream]        frontend/src/api/ai.ts
    → backend/app/api/ai.py resume_chat_send
      → ai_chat_service._chat_context()                     拼装上下文：简历快照 + 历史 + 待确认变更（DB 查询，毫秒级）
      → ① LLM 调用「AI 助手意图识别」                        判断 answer / propose_change / confirm_change / reject_change / clarify
      → ② 若需修改 → LLM 调用「AI 助手生成修改方案」          生成完整 optimized_resume_data（整份简历 JSON）
      → 后处理：deepcopy + 数值校验 + diff 出 suggestions     纯 CPU，毫秒级
      → 保存 assistant 消息（pending_change 待确认状态）
  → 用户点「确认应用」→ decision 接口合并数据（不再调 LLM）
```

关键点：**两次 LLM 调用是串行的**，用户感知延迟 = 意图识别 + 修改方案生成之和。

## 2. 实测耗时排查

### 2.1 数据来源：`backend/logs/ai_model_io.log`

模型 I/O 日志按 `call_id` 记录每次 LLM 调用的 `start` / `output` 事件，配对即可算出单次调用耗时。分析方法（Python 脚本）：

```python
import re
from datetime import datetime

starts, outs, labels = {}, {}, {}
for line in open("backend/logs/ai_model_io.log", encoding="utf-8"):
    m = re.match(r"^(\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}),(\d+)", line)
    if not m:
        continue
    ts = datetime.strptime(m.group(1), "%Y-%m-%d %H:%M:%S").timestamp() + int(m.group(2)) / 1000
    cid = re.search(r'"call_id": "([^"]+)"', line)
    ev = re.search(r'"event": "(\w+)"', line)
    lb = re.search(r'"label": "([^"]+)"', line)
    if not cid or not ev:
        continue
    c, e = cid.group(1), ev.group(1)
    if e == "start":
        starts[c] = ts
        if lb:
            labels[c] = lb.group(1)
    elif e == "output":
        outs[c] = ts

for c in starts:
    if c in outs:
        print(f"{labels.get(c, '?'): <24} {outs[c] - starts[c]:.1f}s")
```

### 2.2 实测结果（deepseek-v4-flash-vision-exp，OpenAI 兼容接口）

| 阶段 | 实测耗时 | 说明 |
|------|---------|------|
| ① 意图识别 | 0.8 ~ 1.8s | 输出只有几行 JSON |
| ② 生成修改方案 | **26.6 / 32.5 / 50.1s** | ⚠️ 瓶颈 |
| 对话回复（不修改） | 2.9 ~ 9.8s | 正常 |
| 简历生成 | 13.7 ~ 92.6s | 整份生成，输出量大 |
| 简历评分 | 51.0s | |
| DB + 后处理 | 毫秒级 | 可忽略 |

「改地点」全程 ≈ 30~50s。

### 2.3 瓶颈根因：输出 token 数决定延迟

- 修改方案调用要求模型返回**整份简历的 `optimized_resume_data`**（work/projects/education 全部重写）
- 实测：输入 prompt ≈ 12.8KB，输出 ≈ 10KB JSON（≈ 3000+ token），逐 token 生成下就是 30~50s
- 改一个地点是极端案例：**99% 的输出都是原样复述**
- 隐患：`.env` 的 `AI_TIMEOUT=60`，50.1s 已贴近超时线

### 2.4 优化方向

1. **增量输出**：让模型只返回被修改的 section，后端用 `_merge_confirmed_resume_data` / `_resume_preserve_snapshot` 合并 —— 输出量降一个数量级，预期延迟降到 ~5s。代价：list 类 section 无法增量合并（见下文第三节的取舍）
2. **前端走流式接口**：`/stream` 端点已存在，流式可让 reply 文字提前显示，改善感知延迟（应用变更仍需等完整 JSON）

## 3. 一致性保障：模型整份返回时，未修改内容如何不被改坏

**核心思想：信任边界在服务端，不在模型。** Prompt 只是礼貌请求，真正的保证是四层防御：

### 第一层：Prompt 约束（软约束）

`prompts.py`：

- L108：「保留当前简历中未被用户要求改变的 avatar、field_config、custom_fields、layout、custom_sections 和全部正文模块」
- L63：「优化已有简历时必须保留原有 id、未修改字段和未修改条目」

LLM 可能漏抄、幻觉，系统**并不信任这一层**。

### 第二层：后端快照保护（非正文配置绕开模型）

`ai_chat_service.py:132` `_resume_preserve_snapshot`：调模型前把最易丢失的**非正文配置**（avatar、field_config、custom_fields、layout、custom_sections）deepcopy 快照，独立通道保护。

### 第三层：合并时分级覆盖（核心硬约束）

`ai_chat_service.py:346` `_merge_confirmed_resume_data`：

```python
merged = {**current, **optimized}        # ① 顶层：模型没返回的 key 自动用旧值兜底
for key in ("basics", "layout"):
    merged[key] = {**current_section, **optimized_section}   # ② dict 字段级合并
```

- ① 模型 JSON 漏掉整个 section → 旧值兜底
- ② basics/layout 字段级合并 → 模型只改 location 时漏抄的 avatar 也会被保留
- ⚠️ list 类型（work/projects/education）**整段替换**：模型漏抄一条经历，这层救不回来 → 靠第四层

### 第四层：事后校验 + diff + 人审

| 机制 | 位置 | 作用 |
|------|------|------|
| 数值防幻觉 | `_unverified_numeric_claims` (L456) | 简历和对话中都没出现过的量化结果（如凭空 +78%）→ 直接拒绝写入 |
| 声明范围比对 | `_model_declared_change_issue` (L540) | 意图识别声明的 target_sections 与实际 diff 是否一致 |
| 实际变更 diff | `_actual_change_suggestions` (L492) | 逐 section 对比新旧数据，生成「已修改：基本信息（所在城市）」清单 |
| 待确认机制 | pending_change 状态 | 所有修改先进待确认状态，用户点「应用」才真正写入 |

### 设计取舍

整份返回换来 diff 完全可控：后端拿新旧两份完整数据做纯代码对比，不依赖模型"汇报"自己改了什么。代价是慢（第 2.3 节）—— 慢与稳的权衡是这条链路最核心的设计决策。

## 4. LangChain / LangGraph 的具体角色

**一句话：LangChain 负责"每一次 LLM 调用"本身；LangGraph 只在 JD 匹配优化场景负责"多步调用编排"。**

### 4.1 LangChain 的四个接入点

| 层 | 文件 | 组件 | 作用 |
|----|------|------|------|
| 模型接入 | `ai/llm.py` | `ChatOpenAI` | 全项目唯一 LLM 客户端，OpenAI 协议兼容任意服务商，配置动态读取支持热切换 |
| 提示词 | `ai/prompts.py` | `ChatPromptTemplate` | 所有 prompt 模板化，system + human + 变量注入 |
| 调用编排 | `ai/chains.py` | LCEL 管道 `prompt \| get_llm()` | 统一封装 invoke/stream、JSON 解析、Pydantic 校验、失败修复、token 统计 |
| 结构化输出 | `ai/schemas.py` | Pydantic BaseModel | 每个 AI 功能一个 schema（ResumeChatIntentResult、ResumeChatResult 等） |

通用调用封装：

```python
chain = prompt | get_llm()          # LCEL 管道
_invoke_json(prompt, payload, Schema)
#   → invoke → 剥离 <think> → JSON 解析 → Pydantic 校验 → 失败则 _repair_json_content 二次修复
```

### 4.2 LangGraph 的唯一使用点：JD 匹配优化

`ai/graphs.py`：

```python
graph = StateGraph(JdOptimizeState)      # TypedDict 共享状态
# 8 节点串行：分析JD → 分析简历 → skills → projects → work → summary → 评分 → 汇总
```

- 每个节点内部仍是 LangChain 管道（`JD_NODE_PROMPT | get_llm()`）
- 每个节点 `deepcopy(state["optimized_resume_data"])` 后只改自己负责的 section，最终结果是所有节点修改的累积
- **为什么这里需要图**：8 次串行 LLM 调用，前序产出（JD 关键词、匹配分析）流入后续节点当上下文，单节点失败可独立修复

### 4.3 设计选择评价

项目只用了 LangChain 很薄的一层（模型抽象 + PromptTemplate + LCEL），**没有用** Memory、Agent、OutputParser —— JSON 修复、数值校验、快照保护、模型 I/O 日志全部自研。轻依赖、可控性强，代价是自行维护这些组件。

单步调用（意图识别/修改方案/回复）不用图 —— 用 LangGraph 反而是过度设计。
